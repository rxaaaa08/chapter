# chapter அ — Claude Code guide

Mobile-first social-experiences booking webapp (React + Vite + TypeScript, Supabase backend, PayU payments, AiSensy WhatsApp). Deployed from `main`. The owner is a **no-code founder**: explain plans and tradeoffs in plain language; never assume they can edit code or config themselves.

## Golden safety rules
1. **The Supabase DB is PRODUCTION with live customers.** For test rows use phone `90000000xx`, verify writes with `RETURNING`, and delete test rows afterwards. Never mutate rows whose status is `advance_paid`/`fully_paid` without explicit instruction — guard UPDATEs with `status not in ('advance_paid','fully_paid')`.
   - **`public.app_secrets` is guarded twice on purpose (2026-09-18): deny-all RLS AND no `anon`/`authenticated` table grants.** It holds the shared secrets the database itself injects into outbound calls (`admin_push_secret`, `meta_alerts_secret`, `whatsapp_log_secret`, `release_log_secret`, `purge_passcode`). Never grant either client role anything on it, and never add an RLS policy without first reading why it has none — for a long time RLS was the *only* thing between a browser session and every secret in it. Its legitimate readers are `SECURITY DEFINER` functions owned by `postgres`, or `service_role`; neither is affected by those grants. Same one-mechanism-vs-two argument as `meta_audience_membership`.
   - **When verifying in SQL, make assertions return ROWS.** The Supabase MCP's `execute_sql` returns only the LAST statement's result and never surfaces `RAISE NOTICE`, so a `DO $$ … $$` block of checks prints nothing and looks exactly like one that passed. Use a temp table and `SELECT` it last. Silence from an assertion is not evidence.
2. **GOLDEN RULE (owner, 2026-09-19): nothing is pushed until the owner agrees.** This binds every agent — interactive Claude sessions, OpenClaw, and any worker or sub-agent any of them starts. No `git push`, no pull request, without the owner's explicit OK in that conversation turn; an OK for one push is not an OK for the next. Before any push, list every commit going out (`git log origin/main..HEAD`) with OpenClaw's marked, for him to OK. **Why:** the Meta ads system is still being built and perfected locally, and he wants it perfect before anything reaches the live site — speed of shipping is explicitly *not* the priority. Pushing to `main` also deploys the live site.
   - **Local commits:** interactive Claude sessions still commit only with his OK. **OpenClaw and its workers MAY make local commits without asking** (owner, 2026-09-19 — commits are the undo history for unattended runs), on these terms: the message starts with `[openclaw]`; stage **only the files that agent changed**, by path — never `git add -A` / `git add .`, which would sweep in the owner's or another session's uncommitted edits; never amend, rebase, reset or rewrite existing commits; undo is `git revert`, done in an interactive session. The repo's pre-commit secret scanner (`.githooks/pre-commit`) must never be bypassed (`--no-verify` is forbidden).
   - **Deploys and prod DB changes do NOT need a per-change OK** (owner, 2026-09-19: per-change interruptions would defeat hours-long autonomous runs) — rule 3 governs how. OpenClaw starts with **no** live access; when it is given some, the payment-path functions (`create-payu-order`, `payu-callback`, `payu-webhook`, `verify-pending-payments`) stay excluded from unattended deploys.
3. **Deploying edge functions is allowed** (the deny rules were lifted 2026-08-26) — but the things below must never be got wrong.
   - **ALWAYS pass `--no-verify-jwt`** for any function a customer, PayU, or a cron reaches. There is no `supabase/config.toml`, so the CLI defaults `verify_jwt` to **true** when the flag is omitted — deploying `payu-callback` or `payu-webhook` without it makes PayU's unauthenticated POST return 401 and **payments stop**. Currently `verify_jwt: false` (deploy WITH the flag): `create-payu-order`, `payu-callback`, `payu-webhook`, `verify-pending-payments`, `capi-lead`, `cart-abandonment`, `get-user-context`, `open-event-otp`, `retarget-check`, `brevo-webhook`, `send-admin-push`, `meta-ads-sync`, `meta-ads-webhook`, `meta-audience-sync`, `meta-ads-alerts`, `meta-insights-features`, `meta-catalog-feed` (Meta fetches it unauthenticated), `meta-signal-watchdog` (daily cron). Currently JWT-verified (deploy WITHOUT it): `send-push-notification`, `send-aisensy-invite`, `send-brevo-invite`, `creator-signup`, `marketer-signup`, `whatsapp-reply`. **This list was verified against `list_edge_functions` on 2026-09-16** (all 24 functions) — on 2026-09-08 three Meta functions were live with `verify_jwt: false` but missing from this line, and on 2026-09-11 two more (`meta-ads-alerts`, `meta-insights-features`) still were, which is the failure mode this rule exists to prevent. Re-verify rather than trusting the list.
   - **`supabase/functions/_shared/*` is bundled at DEPLOY time**, so editing it changes nothing live until *every* importer is redeployed — and nothing warns you. This silently cost us two Meta reporting gaps (see the `edge-function-shared-module-drift` memory). Importers of `_shared/metaCapi.ts` (**five**, and the list grows): `payu-callback`, `payu-webhook`, `verify-pending-payments`, `capi-lead`, `meta-audience-sync`. The last one imports only the hashing helpers (`sha256Hex`, `normalise*`) so Custom Audience uploads hash identically to CAPI — miss it on a redeploy and audience matching silently drifts from event matching. **Re-derive this list with `grep -rl "_shared/metaCapi" supabase/functions/` rather than trusting it.**
   - **`--no-verify-jwt` does NOT mean "unauthenticated" for two of these.** `send-admin-push` requires the header `X-Admin-Push-Secret`, and since 2026-09-18 `meta-ads-alerts` requires `X-Meta-Alerts-Secret`; both compare against a row in `public.app_secrets` and answer **401** otherwise, **503** if the row is missing. The platform flag stays `false` because pg_cron sends no JWT — the gate lives in the function body instead. Three consequences: a bare curl at either URL returning 401 is the system **working**, not broken (META-ADS-HANDOFF.md §11 has the SQL that invokes them properly); never "simplify" that gate away, because `meta-ads-alerts` spends real Meta API quota on every call and an open endpoint that does so is how an ad account gets its quota cut by Meta; and a fresh environment needs the `app_secrets` row or the function refuses everything.
   - **Putting a secret in front of an endpoint a cron already calls? Ship the CRON change FIRST, the function second.** This is the reverse of the usual order and it is not a style preference. A cron sending a header the live function ignores is harmless; a function demanding a header the cron does not send is a 401, and pg_net does not retry — every Meta cron runs once a day, so that is a whole day of silence, with no alarm. Done this way for `meta-ads-alerts` on 2026-09-18.
   - After any deploy, verify with the Supabase MCP `list_edge_functions`: `updated_at` must have moved **and** `verify_jwt` must still read what the list above says.
4. **Deploy hold:** none active — the open-event batch (`src/App.tsx`, `src/AppFlow.tsx`, `src/PaymentOverlay.tsx`, `supabase/functions/payu-callback`, `supabase/functions/cart-abandonment`) was shipped on 2026-07-05. Still prefer isolated, one-concern commits and verify with `git status --short` before and after committing. If a new hold is put in place, record its file list and "active" status here.
5. Local `npm run dev` talks to PROD Supabase — UI testing creates real rows and real admin notifications.

## Domain facts
- `events.booking_url`: `native-application` = invite-only · `payu-hosted` = open event · community events use `booking_flow='whatsapp'`. `booking_flow` is NOT NULL, CHECK (`payment`|`whatsapp`).
- `events.payment_mode`: `split` (advance + balance) | `full` (single payment → `fully_paid` directly).
- `applications.status`: `pending → invited → advance_paid → fully_paid` (+ `waitlist`/`rejected`). Open events have no approval: `pending` = "in progress". Display-only flags: `cart_abandoned`, `re_target`; `recovered_at` = paid after abandoning (badge, not a status).
- Unique key `applications(event_slug, phone)`; phones stored as last-10-digits.
- Per-date timelines: `event_dates.booking_steps` (JSONB). Always prefer the applicant's `selected_date` steps over event-level fallback. **Never read a step by index** — the row count and order change per model (invite full=4/split=5, open full=3/split=4), which is what silently blanked the meeting date in the /invite greeting for single-payment events. Use `stepRole()` from `src/bookingTimeline.ts`; the two edge functions that can't import it carry a mirrored regex with a matching comment.
- **`src/bookingTimeline.ts` is the single definition of a booking timeline** — the six row tables, `stepRole()`, `stepsMatchModel()` (heal stale steps), and `stepBadge()` (which pill a row gets, and therefore whether its date is ever shown). The admin editor (`AdminPanel` Flow ▸ Timelines), the `/plans` timeline (`AppFlow`) and the `/invite` timeline + receipt (`App`) all read from it. Before adding a row table or a "which row is this" regex anywhere, put it here instead — four hand-kept copies is what let the editor offer date pickers on rows the guest never sees a date on. `stepBadge() === 'date'` is the ONLY case where a row's stored date reaches a customer; the editor shows a static pill otherwise and blanks the date on save (`stripDeadStepDates`).
- RLS: anon cannot SELECT `applications`/`invited_numbers`/`invite_payment_submissions` — use `get-user-context` or the `event_booking_counts(_by_date)` RPCs.
- Marketers: `event_marketers` maps events→marketers; round-robin assignment trigger on application INSERT; commission accrues on `fully_paid` — **but NOT on open events: since 2026-09-18 `accrue_marketer_sale()` and `accrue_manager_sale()` return early on `is_open_event()`** (owner's decision, 2026-08-10 and restated 2026-09-18). Assignment still happens on open events — the manager owns the lead, the brief and the scorecard, unpaid. **Never enforce that rule by clearing `events.marketer_commission`**: NULL there falls through to the person's own `commission_amount`, which is how ₹875 was paid by accident (META-ADS-HANDOFF.md §21.8). Copied events inherit marketer mappings.
- **`applications` records current state, not history — several fields overwrite the past in place.** `assigned_marketer_id` re-stamps on unpaid leads when an event's marketers change; `selected_date` is mutable (a marketer rolling a lead to the next date leaves no trace); `cart_abandoned` is never cleared once set; slugs/titles drift on copied events; `affiliate_id` re-attributes at payment. **Any per-date or per-marketer cohort analysis of historical data is therefore unreliable** — both of those produced confidently wrong answers on 2026-08-07/08. Since 2026-08-08 the `application_events` table (trigger `trg_zz_log_application_change`, readable via the `application_history` view) records every change to status / selected_date / marketer / manager / affiliate / call_status / cart_abandoned / recovered_at / city / pickup with a timestamp and role. Append-only: is_admin_strict SELECT only, and INSERT/UPDATE/DELETE/**TRUNCATE** revoked from anon+authenticated (TRUNCATE bypasses RLS). Rows before 2026-08-08 are `field='baseline'` snapshots, NOT observed history. The trigger swallows all exceptions so logging can never roll back a booking.
- Commission attribution is **pinned to the booking row, never resolved live at payment time** — `applications.assigned_marketer_id` and `applications.assigned_manager_id`, both stamped on INSERT and read by the accrual triggers. This is what stops a late/bulk `fully_paid` flip from paying whoever happens to be assigned today (that bug hit managers live on 2026-08-02). Changing an event's marketers/manager re-stamps only leads whose `status NOT IN ('advance_paid','fully_paid','rejected')`; anything that took money keeps its original owner. One manager per event is enforced by `uq_event_managers_event`, so a handover is always remove-then-add.
- Open-event payment gate (`create-payu-order`): a NEW open-event ticket requires a verified `open_event_otp_sessions` token, EXCEPT two deliberate skips — a prior `payu_payments` row for this event+phone (failed-attempt **recovery** deeplink) or a matching `doubt_submissions` row (event + phone + email). An existing `applications` row is intentionally NOT accepted as proof (anon can self-INSERT a `pending` row). Balance payments never re-OTP. OTP rate limits are per-channel: WhatsApp 2/10min keyed by phone, email 2/10min keyed by email (email fallback also needs a valid prior WhatsApp session).

- **Delivery logging (both channels).** `whatsapp_sends` + `whatsapp_inbound` + `whatsapp_send_events`, and since 2026-09-01 `email_sends` + `email_send_events` mirroring them. Email's claim-by-INSERT unique index `(application_id, kind)` is a **send guard, not just a log** — it replaces the old `email_invite_sent` / `payment_failed_email_sent` style booleans, which were claimed *before* a send. Never "simplify" it into a post-send log row. `verification_code` is excluded from the index so OTP resends work. Delivery ticks render in **People ▸ Call only**; the Chat view stays WhatsApp-only. Full spec: `DELIVERY-LOGGING-HANDOFF.md`.
- **WhatsApp click tracking** needs the template's button URL approved as `https://api.wamafy.com/r/{{1}}`, and then the send passes the **full destination URL** instead of the placeholder tail — the meaning of `value` flips, and the wrong shape is a 400 that stops the message. Only `invitation_with_tracking` is converted; copy the try-then-fallback pattern in `send-aisensy-invite` before converting any other. **Never convert `otp`** (copy_code button, gates every open-event sale).

## Workflow preferences
- **Build systems for the scale we are heading to, not the scale we are at.** Owner-stated 2026-09-06, after a proposal was scoped down because no ad money had been spent yet. Current volume is NOT a reason to defer infrastructure — "we haven't spent anything on ads yet" is exactly when the measurement plumbing has to be laid, because data not captured on day 1 is gone forever and cannot be backfilled. Judge a proposal by whether it still holds at 50x the volume. Small *sample* is a legitimate caveat on reading a chart; it is never an argument against building the pipe that fills it. Say the caveat once, then build the thing.
- **Do not push the owner toward launching.** Owner-stated 2026-09-07, after several replies ended with a "now go run your first ad" checklist. He sets the pace and will say when he is ready. Until he does, the work is *building and perfecting systems*, not getting started. Answer what is asked, build what is asked, and leave the readiness judgement to him — a closing "next step: launch" is exactly the nudge he does not want. This does NOT mean hiding a genuine deadline: if something is irreversible if missed (traffic arriving before `{{ad.id}}` is set can never be attributed), state the fact once, plainly, and drop it.
- **Write the work down where it outlives the conversation — in the same session, before saying you are done.** Owner-stated 2026-09-21, after a session recorded its own findings into `OPENCLAW-HANDOFF.md` rather than only reporting them in chat. **Why:** a transcript is not a system of record. The next session — or OpenClaw, or the owner weeks later — starts cold, and anything that exists only in a reply is gone the moment it scrolls away, then re-derived at full cost or, worse, re-derived wrongly. He is a no-code founder: he cannot reconstruct it from the code himself. **How to apply:** put it in the in-repo document that owns the topic (`META-ADS-HANDOFF.md`, `OPENCLAW-HANDOFF.md`, `DELIVERY-LOGGING-HANDOFF.md`, this file…), and add a one-line auto-memory pointer when the fact is cross-cutting and would otherwise be buried in a 6,000-line handoff. Record the **measured numbers and the date**, not just the conclusion, so a later session can tell what has gone stale; record the **why and the traps hit**, not just the outcome; and record **negative results too** — "checked X, nothing wrong" that is never written down gets re-investigated from scratch. Then say in the reply where it was written, so he can find it without asking. This applies to findings, decisions, measurements, and anything drafted for later use — not only to code changes.
- One concern per commit; commit messages explain the *why*.
- Ask before anything irreversible or outward-facing (pushes, deletes of non-test data, deploys).
- On "continue where you left off": consult the auto-memory note `open-event-flow-design` first instead of re-exploring code.
